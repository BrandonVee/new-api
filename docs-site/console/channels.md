# 接入第一个渠道

渠道保存网关连接上游所需的信息。先用一个明确支持的模型完成测试，再扩展更多模型和路由规则，比一次导入所有模型更容易定位问题。

## 创建前准备

你需要服务商账号、可用密钥、模型访问权限，以及服务器到上游的网络连通性。上游订阅或客户端会员不一定提供 API 权限，应以服务商授权为准。

## 填写连接信息

进入控制台的渠道管理，新增渠道并设置：

| 字段 | 填写方法 |
| --- | --- |
| 名称 | 能识别用途与环境的名称，例如 `team-chat-primary` |
| 类型 | 按实际服务商选择；兼容接口也要确认具体协议 |
| 上游地址 | 服务商 API 基础地址，或对应部署端点 |
| 密钥 | 服务商发放的凭据；不是 Ai-gateway 的用户登录凭据 |
| 模型 | 选择当前密钥实际允许访问的模型 |
| 分组 | 选择准备授权给用户或令牌使用的分组 |

通常渠道基础地址不应重复填写 `/v1`，前端也会检查这类情况；但个别渠道有专门的路径约定，需依据对应适配器和字段说明。**应用的 OpenAI Base URL 通常带 `/v1`，渠道地址通常是服务商根地址，两者不是同一个配置。**

## 测试与实际请求

1. 保存渠道，运行控制台的渠道测试。
2. 确认测试模型就是准备让应用使用的模型。
3. 为用户配置相应模型价格与权益。
4. 用用户的网关令牌调用 [模型列表](/api/) 和 [Chat](/api/chat)。

渠道测试证明某条上游连接可工作，不能代替用户分组、令牌权限和余额验证。列表能看到模型，也不一定证明上游有对应模型权限。

## 专有服务商需要额外核对

- Azure 等平台可能要求部署名、资源端点或 API 版本。
- Bedrock、Vertex AI 等平台的身份凭据与区域并不等同于普通 Bearer 密钥。
- 任务插件渠道需先安装并启用对应插件，确认插件支持的模型与原生路由。
- 多密钥渠道应确认轮询与失败处理设置，避免将已失效凭据重复加入。

不要把所有平台都当成同一种 OpenAI 兼容地址来填。上游凭据格式以渠道说明和当前代码为准。

## 修改后的最小检查

每次更换密钥、地址或模型映射后，重新测试受影响模型；查看成功请求的日志和实际命中渠道。已有调用失败时先暂停扩大改动，按 [故障排查](/operations/troubleshooting) 缩小问题范围。
